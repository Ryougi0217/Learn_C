# 第 5 课：编译错误与编译警告

## 本课目标

完成本课后，你应该能够：

- 区分错误（error）和警告（warning）的处理优先级；
- 根据诊断信息定位文件、行号、类别和原因；
- 让一个带警告的程序变成“零警告”构建；
- 理解“能生成可执行文件”不等于“程序一定正确”。

## 1. 编译器诊断怎么读

编译器信息通常包含：

```
文件名:行号:列号: 诊断等级: 具体描述
```

你至少要关注四件事：

1. 诊断来自哪个文件；
2. 指向哪一行、哪一列；
3. 是 `error` 还是 `warning`；
4. 编译器实际指出了什么不匹配。

## 2. 错误与警告的区别

### 错误

错误通常意味着编译器无法继续生成可靠的程序，例如缺少分号、括号不匹配、未知标识符或类型使用不合法。一般需要修复后才能完成构建。

### 警告

警告表示代码可能有问题，但编译器仍能继续。常见例子包括未使用变量、格式说明符与表达式类型不一致、隐式转换可能丢失信息。

警告不是“可以永远忽略的提示”。格式不匹配等警告可能对应未定义行为；未使用变量也可能说明逻辑尚未完成。

## 3. 推荐的编译命令

GCC/Clang 风格：

```
gcc -std=c17 -Wall -Wextra -Wconversion -pedantic practice.c -o practice
```

MSVC：

```
cl /std:c17 /W4 practice.c
```

可以在代码稳定后尝试把警告当成错误：

```
gcc -std=c17 -Wall -Wextra -Wconversion -Werror practice.c -o practice
```

`-Werror` 会让警告阻止构建，适合验收阶段；排查初学者代码时，也可以先不用它，以便看清原始警告。

## 4. 本课练习方式

这次不把整份脚本都挖空：

- `practice.c` 的正常主干可以编译运行；
- `printf` 那一行故意把 `double` 和 `%d` 配错，用来观察 warning；
- `TRY_BROKEN` 分支故意缺少分号，用来观察 error；
- `(void) unused_value` 是一个已经写好的“明确表示暂时不用该变量”的例子。

建议按这个顺序：

1. 不加 `TRY_BROKEN` 编译，保存格式警告；
2. 把格式说明符改成与 `double` 匹配的形式，重新编译；
3. 使用 `-Werror` 确认警告已经清零；
4. 使用 `-DTRY_BROKEN` 编译，定位缺少的分号；
5. 修复后再次用 `-Werror` 编译并运行。

不要把 `-w` 当作修复方法。它只是隐藏诊断，代码本身并没有因此变正确。

## 填空/修改任务

- 先运行默认版本，记录它为什么“能生成程序但仍有警告”；
- 修复格式说明符，让默认构建没有未处理警告；
- 使用 `-DTRY_BROKEN` 复现并修复语法错误；
- 用 `-Werror` 完成最后一次构建；
- 记录每次修改前后的诊断变化。

## 自测题

1. 为什么警告可能比错误更容易被忽略，但仍然值得修复？
2. 编译器指出行号时，为什么要从那一行附近向前检查括号和分号？
3. `-Werror` 改变的是程序逻辑，还是构建策略？
4. 隐藏警告和修复警告有什么区别？
5. 格式说明符错误为什么可能不只是“输出不好看”？
